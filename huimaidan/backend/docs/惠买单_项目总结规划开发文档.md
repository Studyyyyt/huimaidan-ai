## 三、项目阶段总结

- 一期后端：已完成。

## 四、已完成开发内容

### 4.1 一期已完成内容

一期已完成惠买单垫资池模式的核心后端闭环，主要包括：

- 垫资池管理。
- 垫资池充值、调增、调减、启停。
- 垫资池流水记录和预警基础能力。
- 商户优惠规则配置。
- 折扣、立减、积分抵扣三类优惠规则计算。
- 用户端优惠试算。
- 到店买单订单创建、支付、回调处理。
- 支付成功后按商家底价扣减垫资池。
- 惠买单订单列表、详情和基础统计。
- 一期数据库变更脚本和前端对接文档。

### 4.2 二期已完成内容

二期在一期基础上补齐了运营管理与查询能力，主要包括：

- 商户后台经营概览。
- 商户后台结算统计、订单列表、订单详情。
- 商户垫资池流水筛选与导出。
- 平台垫资池列表增强。
- 低余额预警列表。
- 预警历史记录。
- 平台差价日趋势、月度对比、商户排行。
- 平台订单明细导出、商户汇总导出。
- 用户端商户列表、附近推荐、分类、城市筛选。
- 用户端商户详情增强。
- 惠买单用户权益摘要接口。
- 二期数据库变更脚本和前端对接文档。

## 六、开发优先级建议

### 6.1 当前优先级排序

基于项目现状，建议后续开发优先级按以下顺序执行：

| 优先级 | 开发事项 | 原因 |
| --- | --- | --- |
| P0 | 三期提现模式基础字段与订单支付分支 | 这是新资金链路的基础，没有该部分，后续提现接口无法成立 |
| P0 | 三期商户提现申请链路 | 商户端业务闭环核心能力，直接决定提现模式是否可用 |
| P0 | 三期优惠规则与垫资池绑定逻辑调整 | 需要与商户合作模式保持一致，否则规则配置口径会冲突 |
| P1 | 平台提现审核、打款、统计 | 属于提现模式运营闭环，依赖商户端申请链路先跑通 |
| P1 | 三期 SQL、权限、前端对接文档 | 交付必需，但依赖核心接口先稳定 |
| P2 | 三端联调、压测、正式上线准备 | 属于开发完成后的验证与交付阶段 |

### 6.2 不建议当前插入的新需求

在三期提现模式未完成前，不建议插入以下方向的新功能开发：

- 新会员子系统。
- 独立邀请返佣子系统。
- 新佣金提现链路。
- 与提现模式无直接关系的大范围页面改造。

原因是当前主链路风险点集中在“第二套资金结算模式”，继续扩散需求会拉长验证周期并增加资金口径不一致风险。

## 七、后续开发排期建议

### 7.1 建议执行顺序

1. 完成商户结算模式字段与校验。
2. 完成订单创建和支付回调的提现模式分支。
3. 完成优惠规则在不同结算模式下的绑定校验。
4. 完成商户端提现申请、记录、账户维护接口。
5. 完成平台端提现审核、打款、统计接口。
6. 补齐三期 SQL、菜单权限和前端对接文档。
7. 开展联调、压测、上线准备。

### 7.2 里程碑建议

| 里程碑 | 标志 | 建议优先级 |
| --- | --- | --- |
| M1 | 提现模式字段和支付分支可用 | P0 |
| M2 | 商户提现申请闭环可用 | P0 |
| M3 | 平台审核打款闭环可用 | P1 |
| M4 | 三期文档、SQL、权限同步完成 | P1 |
| M5 | 联调、压测、上线准备完成 | P2 |

## 八、当前结论

当前惠买单项目后端已完成前两阶段建设，垫资池模式主链路和二期配套能力已经具备。

接下来的开发重点应明确收敛到三期提现模式，不再分散到无关扩展功能。后续所有开发进度更新，建议统一维护本文件中的“阶段进度总览”“待开发内容”和“开发优先级”三部分，保证项目状态口径一致。
