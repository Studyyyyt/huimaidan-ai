## 1. 文档目的

本文档用于承接 `docs/uniapp/接口对接分析文档.md` 和 `docs/uniapp/小程序开发文档.md`，整理小程序后端后续分批开发内容、接口范围、SQL 交付口径和前端对接文档交付点。

当前原则：

- 先整理文档，再按批次开发。

- 不明确的业务规则先列为待确认，不在实现中猜测。
- 尽量复用现有 CRMEB 和惠买单模块，避免重写一套小程序 BFF。

## 7. 第 2 批：到店买单创建流程与支付解耦

### 7.1 当前冲突

小程序文档希望 P0 打通下单支付页，但 boss 当前要求“暂时先不接入支付”。

新增确认问题：

- CRMEB 原生上架和支付以商品、规格、购物车、商品订单为核心。
- 惠买单没有商品概念，用户进入店铺后输入消费金额，平台按商户优惠规则计算实付金额并结算。
- 因此前端不能为了适配 CRMEB 原链路去创建虚拟商品、加入购物车或选择 SKU。
- 后端需要把惠买单订单明确改造成“商户金额订单”，只保留 CRMEB 订单表作为承载和对账基础，不把商品模型暴露给小程序。

当前代码行为：

- `POST /api/huimaidan/order/create` 会创建订单。
- 创建成功后立即调用 `OrderRepository::pay()`。
- `pay_type` 在 `app/validate/api/HuimaidanOrderValidate.php` 中为必填。

因此，前端如果现在调用 `/api/huimaidan/order/create`，仍然会进入支付准备流程。

### 7.2 已确认方案

boss 已确认采用“拆出创建待支付订单”方案。

本批新增接口只创建惠买单待支付订单，不调用 `PayService`，用于小程序先联调下单页和待支付订单展示。原 `POST /api/huimaidan/order/create` 暂不改语义，避免影响既有支付入口。

新增接口：

```text
POST /api/huimaidan/order/prepare
```

请求：

```json
{
  "mer_id": 1001,
  "amount": "88.00",
  "mark": "用户备注"
}
```

响应：

```json
{
  "group_order_id": 123,
  "order_id": 456,
  "order_sn": "202606110001H",
  "pay_price": "52.80",
  "discount": {
    "rule_id": 1,
    "rule_type": 1,
    "rule_type_label": "折扣",
    "title": "惠买单6折",
    "original_amount": "88.00",
    "pay_amount": "52.80",
    "saved_amount": "35.20"
  }
}
```

### 7.3 去商品化订单改造原则

| 维度 | CRMEB 原商品订单 | 惠买单到店买单订单 |
| --- | --- | --- |
| 下单对象 | 商品/SPU/SKU/购物车 | 商户 `mer_id` |
| 金额来源 | 商品价格、规格价格、数量、运费 | 用户输入消费金额 `amount` |
| 优惠来源 | 商品优惠、购物车优惠、商品券 | 商户优惠规则、后台配置的券/积分抵扣规则 |
| 订单明细 | 商品明细、规格、数量 | 无商品明细，订单快照记录商户、原价、优惠、实付、平台承担金额 |
| 前端流程 | 选商品 → 加购物车/立即购买 → 支付 | 进店/扫码 → 输入金额 → 试算 → 创建待支付订单 |
| 后端约束 | 校验商品上下架、库存、规格、购物车 | 校验商户状态、优惠规则、金额、垫资池/结算模式 |

改造要求：

- `POST /api/huimaidan/order/prepare` 只接收商户和金额，不接收商品、SKU、购物车参数。
- 不要求小程序创建虚拟商品，不依赖商品上下架状态，不校验库存。
- 订单仍可复用 `eb_store_group_order`、`eb_store_order` 承载，但必须通过 `order_scene = 1` 标识为惠买单到店买单。
- `cart_id`、商品明细、规格等字段只能作为 CRMEB 表结构兼容字段，不作为惠买单业务输入。
- 订单详情返回给小程序时，应展示商户信息、输入金额、优惠明细、实付金额，不暴露“商品名称、SKU、购物车”等商品概念字段。
- 支付后置批次接入时，也必须沿用商户金额订单，不回退到商品订单支付链路。

### 7.4 `order/prepare` 最小校验

| 校验项 | 规则 |
| --- | --- |
| 登录态 | 必须登录。 |
| 商户 | `mer_id` 必填，商户存在、未删除、已启用。 |
| 金额 | `amount` 必填，大于 0，最多两位小数。 |
| 商品参数 | 若传入 `product_id`、`sku`、`cart_id`、`cartIds`、`productAttr` 等商品/购物车字段，直接显式失败。 |
| 支付参数 | 本接口不接收 `pay_type`，不调用 `PayService`。 |
| 优惠 | 调用真实优惠引擎生成快照，不能 mock 优惠。 |

## 9. 第 4 批：优惠券和积分真实抵扣

### 9.1 当前状态

本批已实现：

- 查询用户惠买单可用券。
- 优惠试算。
- 订单创建时保存优惠快照。
- 支付型下单接口 `POST /api/huimaidan/order/create` 支持 `couponId`、`usePoints`。
- `POST /api/huimaidan/order/prepare` 不接收真实抵扣字段，避免非支付链路占券或扣积分；但支持 `useMemberDiscount` 用于试算是否参与会员折扣。
- `POST /api/huimaidan/discount/calculate` 支持 `useMemberDiscount`，保证试算和下单口径一致。
- 惠买单订单使用 CRMEB 用户券抵扣，并在事务内核销用户券。
- 惠买单订单使用积分抵扣，并在事务内扣减积分、写入积分账单。
- 券和积分抵扣后与折扣规则按后台配置进行叠加/不叠加校验。
- 订单快照拆分记录优惠券、积分和平台承担金额。

### 9.2 已确认业务规则

| 规则 | 结论 |
| --- | --- |
| 优惠叠加 | 后台管理端可配置“叠加”或“不叠加”。 |
| 承担方 | 优惠券和积分抵扣都由平台承担。 |
| 差价口径 | 券和积分由平台承担，不能减少商家底价金额；是否影响平台差价收入需要在实现中按配置快照明确记录。 |
| 返还规则 | 不设计取消订单状态；支付后退款按后续售后批次全额返还，微信支付退款后置接入。 |
| 非支付链路 | `prepare` 不支持 `couponId`、`usePoints`、`pointsAmount`、`discountType`。 |
| 积分金额 | `pointsAmount` 本批不支持前端指定，`usePoints=true` 时后端自动使用最大可抵扣积分并保留最低 `0.01` 元实付。 |
| 不参与优惠页签 | 业务含义是不参与会员折扣；仍可使用优惠券和积分。前端传 `useMemberDiscount=false`。 |

### 9.3 后台配置建议

新增或复用后台配置项，控制惠买单下单时的优惠计算策略：

| 配置项 | 说明 |
| --- | --- |
| `huimaidan_discount_stack_enabled` | 是否允许折扣、优惠券、积分叠加。 |

优惠券和积分固定为平台承担，不单独配置默认策略。后台未保存 `huimaidan_discount_stack_enabled` 时，下单接口直接报错。

配置必须写入订单优惠快照中的计算结果字段，历史订单不受后续配置变化影响。

## 15. 本轮补充确认

以下口径由 boss 本轮确认，后续实现和文档统一按此执行：

1. 不单独设计“取消订单”状态。
   - 用户进入支付界面后未付款，不生成订单。
   - 已支付订单发生退款时，走全额返还。
   - 后续支付售后批次接入微信支付退款。

2. 优惠券和积分抵扣不做默认策略。
   - 后台未配置对应项时，系统直接报错提示。
   - 不允许静默降级到默认叠加或默认不叠加。

3. 优惠券和积分统计口径需要拆分。
   - 订单快照和统计展示都要分别记录券和积分的承担与统计字段。

4. 第 4 批仍按券和积分一起规划，不拆成两个独立批次。

5. `GET /api/huimaidan/user/assets` 中的 `couponCount` 口径为所有可用券数量。

6. `POST /api/huimaidan/order/create` 与 `POST /api/huimaidan/order/prepare` 的边界保持现状。
   - `prepare` 只创建待支付单，不调用支付。
   - `create` 继续保持创建后直接发起支付。
