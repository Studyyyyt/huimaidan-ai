> 基于《惠买单_技术开发方案_V1.0.md》整理

## 一、优先级总览

```
第一批（P0+P1）：基础底座 + 核心交易闭环 ──────── 第 1-2 轮
第二批（P2）    ：商家/平台管理 + 用户端入口 ──── 第 3 轮
第三批（P3）    ：会员/推广规则扩展 + 测试上线 ───── 第 4-5 轮
```

---

## 二、判定依据

### 2.1 分层原则

| 层级 | 含义 | 判定标准 |
|------|------|---------|
| P0 | 基础底座 | 被 ≥2 个其他模块依赖；必须先于所有依赖方完成 |
| P1 | 核心链路 | 端到端闭环必经节点；P0 就绪后立即启动 |
| P2 | 管理配套 | 运营/商家端必需，但不阻塞用户侧核心链路 |
| P3 | 增长 + 收尾 | 非 MVP 必须；或依赖全链路稳定后再接入 |

### 2.3 为什么不把全部 P2 提前

1. **首页/商家列表**：需要商家数据和优惠规则都已就绪才能展示折扣标签，强行提前会导致返工
2. **商家后台**：需要垫资池流水数据积累才有展示意义，P0+P1 跑几天后接入更合理
3. **平台运营后台**：本质上是对 P1 产出的数据做聚合展示，先有数据再有面板
4. **会员/推广规则**：复用现有等级与统计能力，不新开独立子系统，核心交易跑通后再做规则扩展更稳妥

## 三、第一批（P0 + P1）详细拆解

> **第 1-2 轮**，完成标志：扫码 → 试算 → 支付 → 扣减 → 入账，全链路端到端跑通。

### 3.1 P0-1：垫资池管理（第 1 轮）

#### 3.1.1 任务清单

| 子任务 | 内容 |
|--------|------|
| 数据库建表 | `eb_capital_pool` + `eb_pool_transaction` DDL 执行 |
| Model 层 | `CapitalPool.php` + `PoolTransaction.php`，含关联关系、访问器、修改器 |
| Service 层 | `PoolService.php`：余额查询、充值、扣减（含分布式锁）、流水写入、余额告警检查 |
| 平台端 API | 垫资池列表、单个池详情、平台充值接口 |
| 商家端 API | 垫资池概览（余额/累计充值/累计消耗）、流水列表（只读） |
| 单元测试 | 充值/扣减/并发扣减/负余额透支场景 |

#### 3.1.2 接口契约

**平台充值**：
```
POST /admin/huimaidan/pool/recharge
{ pool_id, amount, remark }
→ 开启 Redis 分布式锁 → 开启事务 → UPDATE balance → INSERT transaction → 提交事务 → 释放锁
```

**扣减（内部方法，支付回调调用）**：
```
PoolService::deduct(pool_id, amount, order_id)
→ 获取分布式锁 → 校验垫资池是否启用
  → 是：UPDATE balance -= amount, INSERT transaction(type=2), 检查告警阈值
  → 否：抛出垫资池不可用异常
→ 释放锁，返回流水ID
```

#### 3.1.3 关键约束

- **原子性**：垫资池状态校验 + 扣减必须在同一数据库事务中
- **并发安全**：Redis 分布式锁 key = `pool:deduct:{pool_id}`，超时 5 秒
- **允许透支**：订单支付扣减允许余额变为负数，但仍需保证垫资池已启用
- **幂等**：同 order_id 重复扣减时幂等返回已有流水记录

#### 3.1.4 交付标准

- 平台管理员可查看所有商家垫资池、执行充值
- 商家可查看本店垫资池余额和流水
- 并发扣减测试通过（10 并发 × 100 次扣减，余额扣减数正确，无超扣）

### 3.2 P0-2：优惠规则引擎改造（第 1 轮）

#### 3.2.1 任务清单

| 子任务 | 内容 |
|--------|------|
| 数据库改造 | `eb_discount_rule` 新增 7 个字段的 ALTER TABLE |
| CRMEB 原表兼容 | 确认原优惠券表结构、评估 ALTER 对原有功能影响、备份方案 |
| Model 层 | `DiscountRule.php`，含三种规则类型的访问器、校验器 |
| 优惠计算引擎 | `DiscountEngine.php`：查询规则 → 逐条计算实付 → 取最优 → 生成快照 JSON |
| 用户端试算 API | `POST /api/huimaidan/discount/calculate` |
| 商家端规则配置 API | 规则 CRUD，关联垫资池 |
| 单元测试 | 三种规则分别计算、取最优、边界值（0.01 / 超大金额） |

#### 3.2.2 计算引擎伪代码

```php
class DiscountEngine {
    public function calculate(int $merId, float $amount): array {
        // 1. 查询该商家所有生效规则
        $rules = DiscountRule::where('mer_id', $merId)
            ->where('status', 1)
            ->where('is_del', 0)
            ->get();

        if ($rules->isEmpty()) {
            return $this->noDiscountResult($amount);
        }

        $bestResult = null;
        $minPayAmount = $amount;

        foreach ($rules as $rule) {
            $payAmount = match($rule->rule_type) {
                1 => round($amount * $rule->platform_discount, 2),
                2 => max(round($amount - $rule->coupon_amount, 2), 0.01),
                3 => max(round($amount - $rule->point_ratio * $amount, 2), 0.01),
            };

            if ($payAmount < $minPayAmount) {
                $minPayAmount = $payAmount;
                $bestResult = $rule;
            }
        }

        $merchantCost = $bestResult->rule_type === 1
            ? round($amount * $bestResult->merchant_cost, 2)
            : $amount;

        return [
            'original_amount'  => $amount,
            'discount_type'    => $bestResult->getTypeLabel(),
            'discount_rule'    => $bestResult->title,
            'discount_rate'    => $bestResult->platform_discount,
            'pay_amount'       => $minPayAmount,
            'saved_amount'     => round($amount - $minPayAmount, 2),
            'merchant_cost'    => $merchantCost,
            'platform_profit'  => round($minPayAmount - $merchantCost, 2),
            'rule_id'          => $bestResult->id,
            'pool_id'          => $bestResult->pool_id,
        ];
    }
}
```

#### 3.2.3 关键约束

- 实付金额最低 0.01 元
- 所有金额保留两位小数，使用 `round(..., 2)` 统一精度
- 快照 JSON 结构固定，后续不可变（否则历史订单对账混乱）
- 规则类型扩展预留：rule_type 用 tinyint，后续可加 4=满减、5=赠品等

#### 3.2.4 交付标准

- 商家后台可配置折扣/优惠券/积分三种规则
- 试算接口正确返回最优优惠方案
- 三种规则混合场景下，正确取实付最小者
- ALTER TABLE 不影响 CRMEB 原有优惠券功能

### 3.4 P1-2：到店买单页（第 2 轮）

#### 3.4.1 任务清单

| 子任务 | 内容 |
|--------|------|
| 扫码入口 | 微信小程序 `wx.scanCode` 调用，解析二维码中的商家 ID |
| 商家信息展示 | 商家名称、Logo、地址、营业状态、可用优惠标签 |
| 金额输入 + 试算 | 复用 P1-1 试算组件 |
| 确认支付 | 调用 `/api/huimaidan/order/create` → 拉起微信支付 |
| 支付结果页 | 成功/失败/取消三种状态页 |
| 异常处理 | 商家不存在、商家已下线、余额不足、支付超时 |

#### 3.4.2 完整交互流程

```
1. 用户点击「扫码买单」或扫描商家桌台二维码
2. 解析二维码 → 提取 merchant_id
3. 调用 GET /api/huimaidan/store/detail/:id → 展示商家信息 + 可用优惠标签
4. 用户输入消费金额 → 实时试算展示优惠
5. 用户点击「确认支付」
6. POST /api/huimaidan/order/create { mer_id, amount, rule_id, pool_id }
   → 后端：
     a. 校验商家/规则有效性
     b. 调用 DiscountEngine 生成优惠快照
     c. 创建订单（状态：待支付）
     d. 调用微信支付统一下单
     e. 返回支付参数（prepay_id, nonceStr, sign 等）
7. 前端 wx.requestPayment 拉起支付
8. 支付结果 → 跳转结果页
```

#### 3.4.3 异常分支处理

| 异常 | 触发条件 | 处理 |
|------|---------|------|
| 商家不存在 | merchant_id 无效 | 提示「商家不存在」 |
| 商家已下线 | status != 1 | 提示「该商家暂不可用」 |
| 垫资池不可用 | 垫资池未绑定、不存在或已停用 | 提示「该商家优惠暂不可用，请联系商家」 |
| 支付超时 | 微信支付未在 5 分钟内完成 | 订单标记为「已取消」 |
| 重复支付 | 同一订单号重复回调 | 幂等处理，返回已有结果 |

#### 3.4.4 交付标准

- 扫码 → 看到商家信息 → 输入金额 → 试算 → 支付 → 结果，全流程 < 10 秒（不含支付等待）
- 垫资池余额不足时，仍可正确完成支付并写入负数余额流水
- 支付回调幂等，同一订单不会重复扣减

#### 3.5.1 任务清单

| 子任务 | 内容 |
|--------|------|

| 订单创建 | `OrderController::create`：参数校验 → 优惠试算 → 写入订单 + 快照 → 调用微信支付 |
| 支付回调处理 | 微信支付回调 → 幂等校验 → 垫资池扣减 → 更新订单状态 → 差价入账 → 触发告警检查 |

#### 3.5.2 支付回调处理流程（核心）

```php
public function notifyCallback(array $wxData): void {
    DB::beginTransaction();
    try {
        // 1. 幂等检查（基于微信订单号）
        $order = StoreOrder::where('order_id', $wxData['out_trade_no'])->lockForUpdate()->first();
        if (!$order) throw new \Exception('订单不存在');
        if ($order->paid == 1) {
            DB::commit();
            return; // 已支付，幂等返回
        }

        // 2. 验证金额一致性
        if ($wxData['total_fee'] != $order->pay_price * 100) {
            throw new \Exception('支付金额与订单不一致');
        }

        // 3. 垫资池扣减（仅垫资池模式商家）
        if ($order->pool_id && $order->order_scene == 1) {
            $txId = PoolService::deduct(
                $order->pool_id,
                $order->merchant_cost_amount,
                $order->id
            );
            $order->pool_transaction_id = $txId;
        }

        // 4. 差价入账
        $order->platform_profit = round($order->pay_price - $order->merchant_cost_amount, 2);

        // 5. 更新订单状态
        $order->paid = 1;
        $order->pay_time = time();
        $order->status = 'pay_success';
        $order->save();

        DB::commit();

        // 6. 异步：余额告警检查（非阻塞）
        if ($order->pool_id) {
            PoolService::checkAlarm($order->pool_id);
        }
    } catch (\Exception $e) {
        DB::rollback();
        Log::error('支付回调失败:', ['order_id' => $wxData['out_trade_no'], 'error' => $e->getMessage()]);
        throw $e;
    }
}
```

#### 3.5.3 订单状态机

```
create → 待支付 (unpaid)
  → 用户支付发起 → 支付中 (paying)
    → 微信回调成功 → 支付成功 (pay_success)
      → 手动完成/自动完成 → 已完成 (completed)
    → 微信回调失败/超时 → 支付失败 → 已取消 (canceled)
    → 退款申请 → 退款中 (refunding) → 已退款 (refunded)
    → 异常 → 异常 (abnormal)
```

#### 3.5.4 交付标准

- 订单创建时优惠快照写入完整 JSON
- 支付回调幂等，重复回调不重复扣减
- 垫资池扣减失败时订单不标记为已支付
- 差价计算与优惠试算结果一致

### 3.7 P1-5：余额预警系统（第 2 轮）

#### 3.7.1 任务清单

| 子任务 | 内容 |
|--------|------|
| 预警阈值配置 | 平台端为每个商家配置 `alarm_balance` + `alarm_enabled` |
| 扣减后检查 | `PoolService::deduct` 完成后异步检查余额是否 ≤ 阈值 |
| 通知触发 | 余额低于阈值 → 平台站内信 + 商家消息通知 |
| 预警列表 | 平台端预警面板（标红显示低于阈值的商家） |

#### 3.7.2 预警触发流程

```
PoolService::deduct() 提交事务后
  → 异步（队列）：检查 pool.balance <= pool.alarm_balance && pool.alarm_enabled == 1
    → 检查距离上次预警时间 > 30 分钟（防骚扰）
      → 是：发送通知 + 更新 last_alarm_time
      → 否：跳过
```

#### 3.7.3 防骚扰策略

- 同一商家 30 分钟内仅发送一次预警
- 预警阈值建议默认值：500 元或最近 7 天日均消耗 × 3，平台可调整
- 不使用短信通知（成本考虑），使用站内信 + 小程序订阅消息

#### 3.7.4 交付标准

- 扣减后余额低于阈值时触发通知
- 同一商家 30 分钟内不重复预警
- 平台端预警面板实时刷新

## 六、风险与缓解

### 6.1 关键路径风险

| 风险 | 影响模块 | 概率 | 缓解措施 |
|------|---------|------|---------|
| CRMEB ALTER TABLE 影响原有功能 | P0-2 优惠引擎 | 中 | 先在测试环境执行 ALTER，全量回归原有优惠券功能 |
| 微信支付审核延迟 | P3 上线 | 中高 | P1-2 开发同时提交审核材料，沙箱环境先行联调 |
| 分布式锁 Redis 故障 | P0-1 垫资池 | 低 | 锁超时兜底（5 秒自动释放），关键场景加数据库乐观锁双保险 |
| UniApp 扫码兼容性 | P1-2 到店买单 | 低 | 多机型测试，降级方案：手动输入商家码 |
| 并发超扣 | P1-3 订单 | 低 | 分布式锁 + 数据库行锁 (`lockForUpdate`) 双重保障 |
