# 惠买单商户唯一店铺二维码开发文档

更新时间：2026-06-17  
适用范围：CRMEB 后端、惠买单商户后台、惠买单微信小程序

## 1. 文档目标

为每个惠买单商户生成唯一店铺二维码，用户扫码后直接进入微信小程序买单页面。  
本次正式方案改为使用微信小程序官方“不限制的小程序码”能力，不再使用 `URL Scheme`。

本方案采用：

- 商户唯一维度按 `mer_id` 落地。
- 后端调用微信 `getUnlimitedQRCode` 生成小程序码图片。
- 商户参数通过 `scene` 传递。
- 商户后台提供查看、下载、刷新能力。
- 管理后台提供查看、检索、强制刷新能力。
- 数据结构保留未来多门店扩展字段，但本次不改成门店主键模式。

## 2. 参考文档

- 微信小程序码能力说明：
  [https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/qr-code.html](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/qr-code.html)
- 获取不限制的小程序码：
  [https://developers.weixin.qq.com/miniprogram/dev/server/API/qrcode-link/qr-code/api_getunlimitedqrcode.html](https://developers.weixin.qq.com/miniprogram/dev/server/API/qrcode-link/qr-code/api_getunlimitedqrcode.html)

结合官方文档，本需求必须注意以下边界：

- 使用 `getUnlimitedQRCode` 时，业务参数必须放在 `scene` 中，不能放在 `page` 参数里。
- `page` 不能带 query，必须是已发布的小程序页面路径。
- `scene` 最大 `32` 个可见字符。
- `scene` 只支持数字、大小写英文及部分特殊字符，不支持 `%`，中文也不能走普通 `urlencode`。
- 成功时接口直接返回图片二进制，不是 JSON。
- 接口限频 `5000 次/分钟`，大量场景建议预生成。
- 小程序码本身适合长期使用，官方说明该类码适用于“需要的码数量极多的业务场景”。

## 3. 当前代码现状结论

### 3.1 小程序当前实际唯一维度

现有小程序买单页实际按 `mer_id` 工作，不存在真正闭环的 `branch_id/store_id` 维度：

- 买单页入口为 `/pages/payment/checkout?id={mer_id}&name={mer_name}`。
- 买单页加载后调用 `GET /api/huimaidan/store/detail/:id`。
- 优惠试算、可用券、下单等核心接口均使用 `mer_id`。
- `store_branch_name` 当前仅作为展示信息，不是独立门店主键。

因此，本次“店铺唯一二维码”必须按 `mer_id` 设计，不能强行做成门店独立主键，否则会和现有小程序实际链路不一致。

### 3.2 为什么仍采用方案 2

本次按 `mer_id` 生成唯一店铺码，但在后端数据结构中预留扩展字段：

- `scene_ext`
- `branch_name_snapshot`
- `entry_code`

这样当前实现完全贴合现状，未来若需要演进到多门店独立二维码，只需要新增真正的 `branch_id` 维度并复用当前模型，不需要整体推翻。

## 4. 总体目标效果

### 4.1 用户侧

用户扫描线下二维码后：

1. 微信直接识别小程序码。
2. 打开指定小程序页面。
3. 页面读取 `scene` 参数。
4. 解析出商户参数。
5. 进入惠买单买单链路并加载真实商户信息。

### 4.2 商户侧

商户后台可：

- 查看当前店铺二维码预览图。
- 下载二维码图片。
- 手动刷新二维码。
- 查看最近更新时间。
- 查看最近失败原因。

### 4.3 平台管理侧

管理后台可：

- 按商户检索店铺二维码状态。
- 查看某商户二维码详情。
- 强制刷新指定商户二维码。
- 查看生成失败原因。

## 5. 总体方案

### 5.1 核心设计

本次不生成跳转链接，不走 H5 中转，也不走 Scheme。

核心链路改为：

1. 后端为商户生成一个压缩后的 `scene` 字符串。
2. 后端调用微信 `getUnlimitedQRCode` 接口，参数包含：
   - `page`
   - `scene`
   - `check_path`
   - `env_version`
3. 微信返回小程序码图片二进制。
4. 后端将图片落库或上传到文件存储。
5. 商户后台展示二维码图片。
6. 用户扫码后，小程序页面从 `scene` 中解析商户参数并进入买单链路。

### 5.2 为什么不能继续沿用当前 checkout URL 形式

当前页面习惯入口为：

`/pages/payment/checkout?id={mer_id}`

但在 `getUnlimitedQRCode` 场景下：

- `page` 不能带参数。
- 参数必须通过 `scene` 传入。

因此本次必须补充小程序对 `scene` 的解析逻辑，不能只依赖现有 `id` 参数入口。

## 6. 小程序入口设计

## 6.1 推荐页面方案

推荐新增一个扫码专用入口页，而不是直接让 `checkout` 承担全部兼容逻辑。

建议页面：

`/pages/scan-entry/index`

理由：

- 当前 `checkout` 页面已经承担真实买单表单、试算、下单逻辑。
- 扫码入口新增后，可以把 `scene` 解析、参数校验、异常提示、跳转行为单独隔离。
- 避免后续再接其他扫码场景时继续污染 `checkout` 页面。

### 6.2 新入口页职责

扫码页负责：

1. 读取 `scene`
2. `decodeURIComponent(scene)`
3. 解析出商户参数
4. 校验参数合法性
5. 跳转到真实买单页：
   `/pages/payment/checkout?id={mer_id}&source=store_qrcode&entry_code={entry_code}`

### 6.3 如果不新增页面

如果团队坚持不新增页面，也可以改造现有：

`/pages/payment/checkout`

让其同时支持：

- `options.id`
- `options.scene`

但这会让买单页承载两套入口逻辑，后续维护成本更高。  
本设计文档默认推荐“新增扫码入口页”。

## 7. scene 参数设计

## 7.1 设计原则

由于微信限制：

- 最长 `32` 个可见字符
- 不支持 `%`
- 不适合塞长 query

所以 `scene` 必须做短参数设计，不能直接写：

`id=1001&source=store_qrcode&entry_code=xxxxx`

这种方案长度不可控，后续扩展也容易超限。

## 7.2 推荐 scene 结构

推荐：

`m{mer_id}.e{entry_code}`

示例：

`m1001.e8F2K9Q`

说明：

- `m` 表示商户
- `e` 表示入口码
- 使用 `.` 分隔，字符安全、长度短

### 7.3 为什么需要 entry_code

虽然当前只按 `mer_id` 落地，但仍建议在 `scene` 中带上 `entry_code`：

- 用于扫码来源标识
- 用于日志追踪
- 用于未来多场景或多门店扩展
- 允许后续只变解析规则，不改线下二维码体系

### 7.4 参数长度控制建议

- `mer_id`：直接使用整数
- `entry_code`：建议 6 到 10 位随机短码
- 整体控制在 20 字符以内

这样后续即使再加一个场景标识，也仍有余量。

## 8. 小程序解析规则

扫码页或买单页在 `onLoad` 中读取：

```ts
const scene = decodeURIComponent(options.scene || '')
```

然后按约定格式解析：

- 读取 `m` 后商户 ID
- 读取 `e` 后入口码

解析成功后跳转或继续执行：

`/pages/payment/checkout?id={mer_id}&source=store_qrcode&entry_code={entry_code}`

解析失败时必须：

- 明确提示“二维码参数错误”
- 禁止静默跳首页
- 禁止使用本地 mock 商户数据兜底

## 9. 数据模型设计

## 9.1 新增表建议

表名建议：

## 10. 后端服务设计

### 10.1 核心服务拆分

建议新增以下服务：

- `HuimaidanStoreQrcodeRepository`
  负责查询、创建、刷新、失效判断。
- `HuimaidanStoreQrcodeSceneService`
  负责生成与解析 `scene` 规则。
- `HuimaidanStoreQrcodeWechatService`
  负责调用微信 `getUnlimitedQRCode`。
- `HuimaidanStoreQrcodeImageService`
  负责保存微信返回的图片二进制并输出图片地址。

### 10.2 生成规则

固定使用：

- `page_path = /pages/scan-entry/index`
- `scene = m{mer_id}.e{entry_code}`
- `check_path = true`
- `env_version = release`

### 10.3 为什么使用扫码入口页而不是直接 checkout

因为：

- 微信接口要求 `page` 不能带参数。
- 当前 `checkout` 现有代码默认认 `id`。
- 新增扫码页能把微信特有入口逻辑和买单业务逻辑分开。

### 10.4 刷新触发条件

以下任一条件满足时重新生成二维码图片：

- 记录不存在。
- 商户手动点击刷新。
- 管理后台强制刷新。
- 小程序页面路径变更。
- `scene` 规则版本变更。
- 历史记录生成失败。
- 二维码图片文件丢失。

### 10.5 关于“有效期”

本方案不再设计 `scheme_expire_time`。  
小程序码本身按官方定位适合长期使用，本次按“长期有效、按需刷新图片”的策略设计。

需要强调：

- “长期有效”不等于“永不重建”。
- 后台仍保留刷新按钮。
- 刷新主要用于：
  - `scene` 规则调整
  - 页面路径调整
  - 图片样式调整
  - 图片丢失补生成

### 10.6 生成失败原则

禁止静默降级，必须显式返回失败原因：

- 微信 access_token 获取失败
- 微信接口返回 `invalid scene`
- 微信接口返回 `invalid page`
- 图片保存失败
- 文件上传失败

如果刷新失败：

- 已有历史可用二维码仍可继续展示，但页面必须提示“刷新失败，当前展示为上一版本二维码”。
- 如果连历史可用版本都没有，则接口直接失败，前端展示“当前无法生成店铺二维码”。

## 11. 微信 getUnlimitedQRCode 调用设计

## 11.1 请求方式

后端调用官方接口，发送 JSON，不可用 form 表单。

### 11.2 请求参数建议

```json
{
  "page": "pages/scan-entry/index",
  "scene": "m1001.e8F2K9Q",
  "check_path": true,
  "env_version": "release",
  "width": 430
}
```

### 11.3 参数说明

- `page`
  必须是已发布的小程序页面，根路径前不带 `/`
- `scene`
  商户参数承载字段，本需求核心参数
- `check_path`
  建议固定 `true`，防止页面路径写错后生成错误二维码
- `env_version`
  正式环境固定 `release`
- `width`
  默认可用 `430`

### 11.4 返回处理

微信成功时直接返回图片二进制。  
后端必须：

1. 判断返回头或内容是否为图片
2. 保存为 png 文件
3. 生成可访问地址
4. 落库记录

如果返回 JSON，则按错误处理。

### 11.5 频率限制

官方文档注明：

- 分钟频率上限 `5000 次/分钟`

因此设计上必须：

- 商户二维码以预生成为主
- 页面不能每次打开都实时向微信请求
- 刷新操作必须带限频保护

## 12. 二维码图片生成与存储

### 12.1 图片来源

图片不是本地自己编码文本生成，而是直接保存微信返回的小程序码二进制内容。

### 12.2 存储规则

建议路径：

`public/uploads/huimaidan/store-qrcode/{mer_id}.png`

如果使用对象存储，则保留统一 URL 返回。

### 12.3 文件覆盖策略

当前一商户只有一个正式店铺二维码，可允许覆盖式更新：

- 文件名可固定按 `mer_id`
- 或使用版本化文件名并更新库中最新地址

推荐首版：

- 文件名固定按 `mer_id`
- 刷新时覆盖原文件

这样商户后台展示逻辑更简单。

## 16. 权限与安全设计

### 16.1 权限

- 商户后台只能查看和刷新自己的 `mer_id` 记录。
- 管理后台可查看所有商户记录。

### 16.2 防篡改

- 二维码参数不直接使用长 query。
- `entry_code` 使用随机短码，便于后续追踪与扩展。
- `scene` 规则统一由后端生成，前端不自行拼装。

### 16.3 防刷

- 刷新接口需要限频。
- 同一商户短时间内重复刷新应拦截，例如 1 分钟内仅允许一次。
- 管理后台强制刷新也要记录操作人和原因。

### 16.4 错误透明

符合“禁止静默降级、禁止隐藏错误”的要求：

- 微信错误码必须落日志并返回前端可读信息。
- 生成失败时后台必须显示原因。
- 小程序解析 `scene` 失败时必须明确提示“二维码参数错误”。

## 17. 埋点与日志

建议新增以下日志或埋点：

- 二维码生成成功次数
- 二维码生成失败次数
- 商户主动刷新次数
- 管理后台强制刷新次数
- 小程序扫码打开次数

至少应记录：

- `mer_id`
- `entry_code`

- 操作来源
- 错误码
- 错误信息

## 18. 验收标准

### 18.1 商户后台

- 商户进入页面能看到二维码预览。
- 点击下载可以拿到可扫码图片。
- 点击刷新后，时间和图片可更新。

### 18.2 管理后台

- 可按商户检索二维码状态。
- 可查看失败原因。
- 可强制刷新指定商户二维码。

### 18.3 扫码链路

- 微信扫一扫可直接进入小程序。
- 小程序扫码入口页可以正确解析 `scene`。
- 最终跳转到买单页并携带 `id={mer_id}`。
- 买单页展示真实商户信息，不依赖本地假数据。

### 18.4 失败场景

- 微信生成小程序码失败时后台有明确报错。
- `scene` 超长或非法时接口明确失败。
- 页面路径错误时接口明确失败。
- 图片文件缺失时下载接口不能返回空成功。

## 19. 非目标

本次不包含：

- 按真实 `branch_id` 的多门店独立二维码
- 多场景二维码体系，例如首页、领券页、活动页共存
- 二维码海报装修能力
- 线下物料打印模板

## 20. 后续可演进方向

如果后续需要多门店独立二维码，可在现有方案基础上扩展：

- 引入真正的 `branch_id`
- 唯一键改为 `(mer_id, branch_id, scene_type)`
- `scene` 规则演进为短编码映射，而不是直接拼接商户信息
- 小程序买单页与下单接口同步支持 `branch_id`
- `scene_ext` 中已有预留字段可平滑迁移

## 21. 本次开发建议结论

本次按方案 2 实施，但能力基座改为微信官方“小程序不限码”：

- 当前唯一维度以 `mer_id` 为准
- 使用 `getUnlimitedQRCode`
- 商户参数通过 `scene` 传递
- 推荐新增扫码入口页解析 `scene`，再跳买单页
- 商户后台与管理后台都提供查看、下载、刷新能力
- 数据模型预留未来多门店扩展字段，但本次不提前改造小程序主链路

这是与当前代码现状最一致、且与微信官方二维码能力最匹配的实现方案。
