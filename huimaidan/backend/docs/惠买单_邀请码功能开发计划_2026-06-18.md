# 惠买单邀请码功能开发计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` or `superpowers:executing-plans` to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 用户扫码进入微信小程序后完成邀请绑定；后台可配置“邀请一个用户奖励多少积分”和“邀请奖励上限”，并复用现有会员成长值体系实现邀请达标后自动升级会员等级。

**Architecture:** 复用 CRMEB 已有推广关系字段 `eb_user.spread_uid`、绑定方法 `UserRepository::bindSpread()`、积分账单类型 `integral/spread`、会员成长账单类型 `sys_members/member_share_num`、平台积分配置页和会员配置/等级页。小程序扩展现有扫码入口 `/pages/scan-entry/index`，新增 scene 格式 `i{uid}`，例如 `i12345`，解析后把邀请人 UID 透传到登录、手机号绑定和已登录绑定接口。

**Tech Stack:** ThinkPHP 6 / CRMEB MER v3.4、Vue 2 + Element UI admin、uniapp Vue 3 + TypeScript、微信小程序码 `scene`。

---

## 已确认口径

- 邀请码 scene 直接使用用户 UID：`i{uid}`。
- 不新增邀请码映射表，不做短码失效、重置、统计。
- 邀请绑定复用现有用户上级关系：被邀请人的 `spread_uid = 邀请人 uid`。
- 邀请奖励积分复用现有配置 `integral_user_give`。
- 新增“邀请奖励上限”配置：限制同一邀请人最多可通过邀请获得多少次积分奖励。
- 会员升级复用现有成长值体系，不新增独立“邀请人数直升会员等级”规则。
- 邀请成功后保留现有 `UserBrokerageRepository::incMemberValue($spreadUid, 'member_share_num', 0)` 调用；后台通过“邀请获得成长值”和会员等级“所需成长值”动态配置，例如邀请 200 人升级时配置每次邀请成长值为 1、目标等级所需成长值为 200。
- 禁止静默降级：scene 解析失败、接口失败、二维码生成失败、登录透传失败必须显式报错或 toast。

## 数据库与配置设计

### 新增系统配置

新增系统配置 key：

- `integral_user_give_limit`
- 类型：整数
- 默认值：`0`
- 语义：邀请奖励上限。`0` 表示不限制；大于 `0` 表示同一邀请人通过邀请好友最多获得 N 次积分奖励。
- 只限制积分奖励，不限制邀请关系绑定。即超过上限后仍可绑定 `spread_uid` 和增加 `spread_count`，但不再增加积分账单。

### 会员成长值动态配置

本需求不新增会员相关数据库字段，复用现有字段和后台页面：

- 会员总开关：`member_status`
- 邀请获得成长值配置：`member_share_num`
- 会员等级类型：`user_brokerage.type = 1`
- 会员等级所需成长值：`user_brokerage.brokerage_rule.value`
- 用户当前成长值：`eb_user.member_value`
- 用户当前会员等级：`eb_user.member_level`

“邀请 200 人升级会员”等需求通过现有成长值体系配置实现：

- 后台开启会员功能。
- 后台设置 `member_share_num = 1`，表示每成功邀请 1 个用户给邀请人增加 1 点成长值。
- 后台把目标会员等级的所需成长值配置为 `200`。
- 邀请人每成功绑定一个新用户，现有 `bindSpread()` 会调用 `incMemberValue($spreadUid, 'member_share_num', 0)` 增加成长值。
- `checkMemberValue()` 会根据会员等级所需成长值自动升级，并写入 `sys_members/member_upgrade` 账单。

注意：会员升级会消耗对应成长值，这是现有 `decMemberValue()` 逻辑决定的业务行为。本计划复用该行为，不额外实现“累计邀请人数不消耗成长值直升会员”的规则。

### 微信身份与未注册新用户处理设计

新用户扫码进入小程序时，不会自动授权手机号，也不一定已经存在正式 `eb_user.uid`。因此邀请链路不能依赖手机号，也不能把 `appid` 当作用户唯一标识。

正确口径：

- `appid` 是小程序应用标识，所有用户相同，不能作为用户唯一标识。
- 小程序内用户唯一身份优先使用微信返回的 `openid`，本项目落库字段为 `wechat_user.routine_openid`。
- 如果微信开放平台已打通，可同时保存 `unionid`，用于跨公众号/小程序/App 合并身份；但本小程序内识别仍以 `routine_openid` 可用为前提。
- 系统内部业务关系仍绑定到正式用户 `eb_user.uid`，不能直接绑定到 `openid`。

现有代码已经具备未注册阶段的身份锚点：

- 前端调用 `wx.login()` 获取临时 `code`。
- 后端 `mp_login_type` 使用 `code` 换取 `openid/session_key`，通过 `routine_openid` 查找或创建 `wechat_user`。
- 若用户未绑定手机号，后端生成 `auth_token`，把 `wechat_user_id`、`user_type`、`spread` 缓存到 `u_try{auth_token}`。
- 前端手机号授权后调用 `mp_phone`，后端通过 `auth_token` 找回 `wechat_user_id` 和 `spread`。
- 若手机号不存在正式用户，后端通过 `syncWechatUser()` 创建 `eb_user`，写入手机号后再调用 `bindSpread($user, $auth['spread'])`。

因此本期实现重点不是新增 `appid` 字段，而是确保扫码得到的邀请人 UID 在以下阶段全程透传：

- `scan-entry` 解析 `i{uid}` 后写入本地 `invite_spread_uid`。
- `getMpLoginType({ code, spread })` 必须传入该 `spread`。
- `mpAuthLogin({ auth: { type: 'routine', auth: { code, spread }}})` 必须传入该 `spread`。
- `mp_phone` 不需要额外传 `spread`，因为后端已通过 `auth_token` 缓存 `spread`。
- 登录失败或手机号授权失败不能清理 `invite_spread_uid`，否则用户重试时会丢失邀请关系。

## 风险与边界

- `i{uid}` 会暴露用户 UID，这是已确认方案的自然结果。
- `appid` 不是用户唯一标识，不参与邀请关系绑定；未注册阶段使用 `routine_openid/wechat_user_id` 暂存微信身份，正式邀请关系仍绑定到 `eb_user.uid`。
- 当前计划不限制邀请关系绑定次数，只限制邀请人获得积分的次数。
- 积分奖励上限不得影响会员成长值；超过积分上限后仍应发放 `member_share_num` 成长值。
- 会员升级复用现有成长值体系，不新增“累计邀请人数直接指定会员等级”的独立规则。
- 如果运营要求“邀请 200 人直接升到指定会员等级且不消耗成长值”，这是独立需求，需要新增规则模型和后台配置，不纳入本计划。
- 当前计划只奖励邀请人，不奖励被邀请人；被邀请人的新人注册奖励仍走 CRMEB 现有 `newcomer_status/register_give_integral`。
- 当前计划不处理老用户已有 `spread_uid` 的覆盖；沿用 `bindSpread()` 现有规则：已有上级不再绑定。
- 当前计划不新增邀请码统计页；可通过用户推广列表和积分日志查看结果。
- 如果微信小程序码使用 `pages/index/index?spid={uid}` 的旧链路，需要首页显式消费 `spid` 参数；如果统一使用 `pages/scan-entry/index`，则必须新增 Task 8 的后端二维码接口。
