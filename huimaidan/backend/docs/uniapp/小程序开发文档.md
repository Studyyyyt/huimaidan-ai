## 一、文档目的

本文档基于以下已有文档整理惠买单小程序开发范围、开发内容、当前进度和开发优先级，供 UniApp 小程序端开发、联调和排期使用。

- `docs/uniapp/API.md`
- `docs/uniapp/接口对接分析文档.md`
- `docs/惠买单_项目总结规划开发文档.md`

本文档只讨论小程序端开发，不包含商户后台和平台后台页面开发。

## 二、当前项目背景

根据项目总结规划文档，当前后端阶段状态如下：

- 一期后端已完成。
- 二期后端已完成。
- 三期提现模式待开发。

这意味着：

- 小程序端与“垫资池模式”相关的核心交易、商户发现、订单查询等能力，已经具备较多可对接基础。
- 小程序端与“提现模式”相关的新业务页面，本阶段不应作为主开发内容。
- 小程序优先开发应围绕“现有已具备或可低成本适配的接口能力”展开。

## 五、接口依赖与开发状态映射

为便于小程序排期，现将接口对接状态直接映射为小程序开发状态：

| 接口状态 | 含义 | 小程序开发状态 |
| --- | --- | --- |
| `✅ 已有接口` | 后端已实现，可直接对接 | 可直接开发 |
| `🔄 可复用接口` | 后端有能力，需适配路径/参数/返回格式 | 可开发，但需先做请求封装和字段转换 |
| `🔧 可扩展接口` | 后端已有基础能力，需扩展聚合字段 | 可开发页面骨架，联调前需后端补充字段 |
| `❌ 需开发接口` | 后端暂无对应能力 | 页面可延期，或先开发静态结构不接真链路 |

### 5.1 当前对接状态对小程序开发的影响

根据 `docs/uniapp/接口对接分析文档.md` 当前统计：

- `✅ 已有接口`：15 个
- `🔄 可复用接口`：20 个
- `🔧 可扩展接口`：2 个
- `❌ 需开发接口`：11 个

由此可见：

- 小程序大部分主流程并非“无接口可用”，而是“可开发但需适配”。
- 真正阻塞页面闭环的，主要集中在少量 `❌` 新接口。
- 当前小程序开发重点应放在先做页面和请求适配层，而不是等待所有接口完全重构后再启动。

## 八、小程序开发内容拆分建议

### 8.1 先开发的内容

建议先启动以下部分：

1. 小程序公共请求层中登录态以当前已对接实现为基线，补齐其它业务接口错误处理。
2. 首页、商户列表、商户详情。
3. 下单支付页、订单列表、订单详情。

原因：

- 这些页面最接近惠买单主业务闭环。
- 对应后端接口大多已有或可复用。
- 可以尽快进入真实联调，提前暴露参数和字段问题。

### 8.2 后开发的内容

建议在主链路稳定后再开发：

1. 我的页面聚合展示。
2. 优惠券、收藏、浏览记录、积分等配套页面。
3. ~~AI 搜索~~ 🚫 **不开发**、统计类、支付结果增强等扩展能力。

原因：

- 这些功能不会决定惠买单主交易是否可跑通。
- 部分能力仍依赖新增接口，过早投入会造成等待和返工。

## 九、关键风险与处理建议

| 风险点 | 影响 | 建议 |
| --- | --- | --- |
| 大量接口为 `🔄` 可复用而非完全同路径 | 前端容易出现字段和路径混乱 | 先建立统一 API 映射层，不在页面里直接写后端原始接口 |
| 登录接口存在二层返回结构 | token 读取路径容易写错 | `/api/auth` 读取 `data.result.token`，手机号绑定读取 `/api/auth/mp_phone` 的 `data.token` |
| 存在 `❌` 新接口 | 个别页面不能完整闭环 | 将相关页面放到 P2，避免阻塞主链路 |
| 用户资产、权益信息来自多个接口 | 我的页面聚合复杂 | 先定义前端 ViewModel，再做数据组装 |
| 支付结果查询接口未完成 | 支付完成后的状态确认存在等待 | 先用支付回调后的订单列表/详情回流兜底，后续再补专门查询接口 |
| 收藏状态查询接口未完成 | 详情页收藏态展示可能不稳定 | 先基于列表态和本地状态更新，后续补查询接口后统一收口 |

## 十、当前结论

当前惠买单小程序开发已经具备进入实际开发排期的条件。

从现有文档判断，小程序端的正确推进方式不是等待所有接口全部“新建完成”，而是：

1. 先做请求适配层。
2. 先做 P0 核心交易页面。
3. 再补 P1 用户配套页面。
4. 最后处理依赖新增接口的 P2 增强能力。

因此，当前小程序开发结论可以统一表述为：

- 文档准备已完成。
- 小程序登录功能已完成对接。
- 可继续启动 P0 核心交易页面开发。
- 后端新增接口不应阻塞首批小程序主流程开发。
