## 三、重启安全须知（重点）

### ✅ 安全的操作（随时可做，不影响数据）

```bash
# 重启 PHP 应用服务（改完代码必须做这一步！）
cd /www/wwwroot/huimaidan.yeeaf.net && php think swoole restart
```

- 只重启 PHP 工作进程，1 秒内完成
- 不动数据库、不动 nginx、不断网
- 用户侧表现：当前请求可能有瞬间抖动，刷新即可

### ✅ 也安全：整机重启

```bash
reboot
```

- 所有服务已配置开机自启，重启后 1-2 分钟自动恢复
- 阿里云控制台重启等同效果

### ⚠️ 需要注意

- **改了 PHP 代码必须 `php think swoole restart`**。这台服务器 Swoole 配置 `hot_update = false`，代码传上去不重启，跑的还是旧代码。这是最容易踩的坑。
- 重启前不用备份，但**改数据库之前**（批量 UPDATE/DELETE）建议先在宝塔面板备份数据库。

## 五、AI 推荐模块排查手册（下次 AI 出问题照这个来）

### 症状 → 排查入口

| 症状 | 先看哪里 |
|---|---|
| 推荐结果固定不变 / 总是那几家 | `eb_huimaidan_ai_recommend_log` 表的 `recall_count` 字段 |
| AI 不回复或回复"服务繁忙" | 当天 error log + `eb_huimaidan_ai_config` 表 `llm_driver` 配置 |
| 推荐结果和问题不相关 | 日志表里的 `intent_tags`（解析出的意图对不对） |
| 商家上传后推荐里找不到 | 该商家的 `city_id`、`eb_huimaidan_merchant_tag` 标签数 |

### 核心排查 SQL

```sql
-- 1. 看最近的推荐记录：召回数 recall_count 是关键
--    = 2~3 说明候选池枯竭（大概率城市/标签问题）
--    = 0 说明一个都没捞到（意图或数据问题）
SELECT log_id, query_text, recall_count, result_mer_ids, rerank_source, create_time
FROM eb_huimaidan_ai_recommend_log ORDER BY log_id DESC LIMIT 20;

-- 2. 看意图解析对不对（intent_tags 里的 category/taste 是否符合用户原话）
SELECT log_id, query_text, intent_tags FROM eb_huimaidan_ai_recommend_log
ORDER BY log_id DESC LIMIT 10;

-- 3. 城市分布是否正常（运营城市的商家数应该占绝大多数）
SELECT city_id, COUNT(*) AS cnt FROM eb_merchant
WHERE is_del=0 AND status=1 AND mer_state=1 GROUP BY city_id;
-- 对照城市表：SELECT id, name, level FROM eb_city_area WHERE id IN (上面的city_id);
-- level=1 是省、level=2 是市。商家 city_id 应该是"市"级 ID！

-- 4. 商家标签覆盖（有标签的商家数应≈总商家数）
SELECT COUNT(DISTINCT mer_id) FROM eb_huimaidan_merchant_tag;
```

### AI 推荐的工作原理（简版）

```text
用户提问 → NLU 意图解析（规则+大模型）→ 按意图标签召回候选商家
        → 规则打分排序 → 大模型动态重排 → 返回前 3 家
```

四个环节各自有兜底，大模型挂了会自动降级到规则排序（日志里 `degraded=1`）。所以 AI 回复慢或文案变朴素 ≠ 系统挂了，先查 `rerank_source` 字段。

### AI 标签运维约定（2026-08-11 数据清洗后生效，加词/加品类照这个来）

**全链路只有一条硬约束：商户标签值必须和词典标签值一字不差。** 所有维护都在后台页面完成，不要直接改数据库。

**1. 词典唯一入口**：后台 AI 管理页 →「AI 标签库」Tab。加同义词、启停词条都在这里，保存立即生效（无需重启）。

**2. 给商家打标签的三个入口**：
- 后台「商家标签管理」Tab：选商家 → 点选标签 → 保存（单个商家维护用这个）
- Excel 导入 `ai_tags` 列：批量用，**值必须照抄词典里的标签值**（导入不校验，写错就召回不到）
- 「重建自动标签」按钮：只重建自动标签（设施/价格/餐段/评分），不会动你手动绑的品类和场景

**3. 新品类上线三步**（例：剧本杀）：
1. 「AI 标签库」新建 `category=剧本杀`，填上同义词（剧本杀店、玩剧本、杀一局…）
2. 「商家标签管理」给目标商家绑定 `category:剧本杀`（自动标签不认识新品类，必须手动绑）
3. 「模拟测试」里问一句"想玩剧本杀"，确认能召回

**4. 标签值格式规范（新建词条时严格遵守）**：

| 类型 | 格式 | 正确示例 | 错误示例 |
|---|---|---|---|
| category/scene/taste/promotion/feature | 中文 | `KTV/酒吧`、`家庭聚餐` | `family`、`ktv` |
| facility | 英文键 | `has_private_room`、`has_parking` | `包间`、`停车方便` |
| price | 裸区间 | `30-60`、`150+` | `人均30-60` |
| meal | 中文 | `午餐`、`晚餐` | `dinner` |

**5. 两条禁令**：
- 同一个概念**不准建第二个词条**——同义词往已有词条里加（重复词条会互相抢词，召回分流错乱）
- 词条**只停用最忌删除**（status 改 0），删了无法追溯

### 新商户接入与标签填写说明（2026-08-11 店名直达上线后）

**一、新商户要进入 AI 推荐，必须满足三个硬条件，缺一个都召回不到：**

| # | 条件 | 在哪设置 | 为什么 |
|---|---|---|---|
| 1 | 有生效中的优惠配置 | 商户后台/平台后台的折扣设置（`eb_huimaidan_merchant_discount` 表 status=1 且在有效期内） | AI 是"优惠商家推荐",**没优惠的商户根本不进候选池** |
| 2 | `city_id` 是**市级** ID | 商户资料 | 省级 ID 会导致同城召回直接过滤掉（2026-08-11 踩过的坑） |
| 3 | 商户状态正常 | 商户审核 | status=1、mer_state=1、未删除 |

**二、各类标签/资料对召回的影响（按影响从大到小）：**

| 项目 | 对召回的影响 | 怎么填 |
|---|---|---|
| **category 品类** | **最硬**。用户说"想吃火锅/想唱歌"时，只推打了对应品类标的商户。一家店可打多个品类 | 后台「商家标签管理」点选，值必须是词典里有的（火锅烧烤/KTV/酒吧/洗浴按摩/中式正餐/特色地方/快餐简餐/小吃夜宵/饮品甜品/西餐异国/养生健康/生活·其他）。**奶茶店记得打"饮品甜品"**（图雅的奶茶馆 2026-08-11 就漏了这个标，用户问奶茶搜不到它） |
| **scene 场景** | 硬过滤。用户说"家庭聚餐/约会/商务"时，没打该场景标的商户会被排除 | 同上，多选：家庭聚餐/朋友聚餐/情侣约会/商务宴请/夜宵/饭后娱乐 |
| **taste 口味** | 硬过滤。用户说"想吃辣的/清淡的"才生效 | 辣/清淡/重口/甜口/酸甜/健康低脂，餐饮必填 |
| **facility 设施** | 硬过滤。用户提"包间/停车/宝宝椅"时，没打的被排除 | 商户资料里勾设施（存英文键 has_*），或「重建自动标签」自动打 |
| **人均消费 per_capita** | 用户指定预算（"人均80以内"）时的硬过滤依据。**不填不会被硬杀，但价格排序会吃亏**，且后台"AI 完整度"会扣分 | 商户资料里填真实人均 |
| **promotion 优惠标签** | 排序权重 15%；用户说"8折"类意图时匹配 | 自动从折扣配置生成，不用手填 |
| **feature 特色** | 只影响排序（高评分/老字号/网红店加权），不影响能不能被召回 | 自动按评分销量生成 + 手动补 |
| **meal 餐段** | 只影响排序（当前时段匹配加分），不做硬过滤 | 「重建自动标签」按营业时间自动打 |
| **评分/销量/距离** | 只影响排序先后：规则打分 = 标签匹配 35% + 距离 25% + 热度 25% + 优惠 15% | 评分销量靠运营，距离靠定位准确 |

**三、店名直达（2026-08-11 上线）：** 用户在对话里直接报店名（如"久湘院子""帮我找一下青口季大排档"）会绕过意图召回直接返回该店，**不要求店名打任何标签**，只要求满足上面三个硬条件。注意：店名格式是"品牌名（分店名）"，用户按品牌名搜会返回各分店（最多 3 家）。

**四、新商户上线检查清单：**
1. 优惠配置生效 → 2. city_id 市级 → 3. 填人均/营业时间/勾设施 → 4. 「商家标签管理」绑 category（必填）+ scene + taste → 5. 点「重建自动标签」→ 6. 「模拟测试」里问一句该品类的话 + 直接问店名，都能召回才算上线完成

**五、词典没覆盖的新品类**（如以后加了剧本杀店）：按上一节"新品类上线三步"走——先加词典词条，再给商户绑标，最后模拟测试验证。

**六、实操示例：顾客口语 → 系统翻译 → 你该打什么标（2026-08-11 实测翻译结果）**

| 顾客口语提问 | 系统翻译（日志 intent_tags） | 商家要被召回必须有 |

## 七、案例存档：2026-08-11 AI 推荐固定几家

**症状**：商家批量上传后，AI 无论怎么提问都固定推荐同 2 家商户。

**根因（三个叠加）**：

1. **城市 ID 错配**（主因）：160 家商家 `city_id` 写成了省级 ID（4736 内蒙古自治区），小程序按市级（4737 呼和浩特市）召回，候选池只剩 2 家。根源是导入代码 `MerchantImportRepository::cityId()` 查城市没限制行政级别。
2. **词典同义词没拆开**：`eb_huimaidan_ai_tag.synonyms` 里存的是顿号连接的长串，代码没拆分，1303 个同义词只有 121 个生效，"火锅" 匹配不到商家的 "火锅烧烤" 标签。
3. **脏词典数据**：后台误建的 `category:火锅`（tag_id 74）和笔误的 `promotion:60折`（tag_id 79）干扰映射。后者也是 error log 里 `Duplicate entry 'promotion-60折'` 的来源。

**修复动作**：

- SQL：160 家商家 `city_id` 4736→4737
- 命令：`php think huimaidan:ai:init-tags` 重建全部商家标签
- 代码补丁 3 个（已同步回本地仓库 `backend/app/common/repositories/huimaidan/`）：
  - `MerchantImportRepository.php` — 城市查询限制 `level=2`
  - `AiTagRepository.php` — 同义词按顿号/逗号拆分
  - `AiNluRepository.php` — 新增 `synonymNormalize()` 意图归一
- 数据清理：删除词典 tag_id 74、79
- `php think swoole restart` 生效

**验证**：火锅/西餐/包间聚餐/清淡四类提问各返回对应品类商家，不再固定。

## 八、案例存档：2026-08-11 下午 商户资料保存失败（3988 字符集错误）

**症状**：商户后台保存商户资料时页面提示错误，error log 大量刷
`SQLSTATE[HY000]: General error: 3988 Conversion from collation utf8mb4_unicode_ci into utf8mb3_general_ci impossible for parameter`。
同一时间小程序短时间打不开（与本次排查中的 Swoole 调试重启窗口重合，属瞬断）。

**根因**：CRMEB 核心表（`eb_merchant` 等 147 张）建库时是 `utf8mb3_general_ci`（不支持 emoji 等 4 字节字符），而应用连接是 `utf8mb4_unicode_ci`。MySQL 8.0.30+ 对预处理语句强制校验：写入含 emoji 的内容直接报 3988。商户在资料里打了 emoji 表情 → 保存失败。**这是 CRMEB 老库的历史问题，与 AI 功能无关。**

**修复**（已执行）：

```sql
-- 全库 147 张 utf8mb3 表批量转换为 utf8mb4_unicode_ci（在线 DDL，不影响读写）
ALTER TABLE `xxx` CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
-- 一键生成脚本：
SELECT CONCAT('ALTER TABLE `', table_name, '` CONVERT TO CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;')
FROM information_schema.tables
WHERE table_schema='huimaidan' AND table_collation LIKE 'utf8mb3%';
```

**验证**：转换后 emoji 写入正常存储回读；剩余 utf8mb3 表 0 张。

**教训**：CRMEB 系老库一律先转 utf8mb4 再上线运营；商户文案里带 emoji 是常态。

## 九、紧急联系路径

搞不定的标准动作：

1. 导出当天 error log：`runtime/log/日期_error.log`
2. 导出推荐日志表前 20 行（上面第五节 SQL 第 1 条）
3. 把这两样 + 问题现象描述发给技术方
