# 惠买单微信支付 v2 对接说明

更新时间：2026-06-15

## 1. 本次目标

本次处理目标不是重写 CRMEB 支付能力，而是：

1. 复用 CRMEB 后端现有惠买单下单支付接口。
2. 将 uniapp 结算页真正接到 CRMEB 已有的支付返回结构。
3. 按微信支付 v2 小程序支付参数格式，修正 `uni.requestPayment` 调用。
4. 修正支付成功后的订单详情跳转链路。
5. 输出可落地的联调说明，避免后续再误判“后端没接口”或“前端没调起支付”。

## 2. 结论

### 2.1 当前项目实际支付入口

当前 `huimaidan-uniapp` 结算页实际使用的是：

- `POST /api/huimaidan/order/createCombined`

不是旧的：

- `POST /api/huimaidan/order/create`

原因是当前买单页已经采用“双金额模型”：

- `discount_amount`：参与会员折扣、优惠券、积分。
- `no_discount_amount`：不参与任何优惠。

该模型与 `createCombined` 设计完全一致，因此本次继续沿用 `createCombined`，不回退到旧接口。

### 2.2 微信支付 v2 是否支持

CRMEB 小程序支付底层本身支持 v2 / v3 双栈。

是否走 v2，不由前端决定，而由 CRMEB 小程序支付配置决定：

- 配置项：`pay_routine_type`
- `0`：微信支付 v2
- `1`：微信支付 v3

本次前端适配后的逻辑，对 v2 / v3 都兼容：

- v2 时 `signType` 通常为 `MD5` 或 `HMAC-SHA256`
- v3 时 `signType` 通常为 `RSA`

前端不再写死签名类型，只透传后端真实返回。

## 3. 本次复用的后端能力

本次没有新增惠买单支付后端接口，直接复用 CRMEB 现有接口和支付服务：

### 3.1 下单支付接口

- `POST /api/huimaidan/order/createCombined`

控制器：

- `app/controller/api/huimaidan/Order.php`

仓储：

- `app/common/repositories/huimaidan/OrderRepository.php`

作用：

1. 创建惠买单订单。
2. 调用 CRMEB 现有 `PayService -> MiniProgramService` 支付能力。
3. 返回 CRMEB `status()` 包装后的支付数据。

### 3.2 支付结果查询接口

- `GET /api/huimaidan/order/pay_result/:id`

作用：

1. 按 `group_order_id` 或 `store_order_id` 查询惠买单支付结果。
2. 返回：
   - `paid`
   - `orderId`（group order）
   - `storeOrderId`（真实订单详情 ID）
   - `payTime`

本次前端支付成功后，使用该接口兜底获取真实 `storeOrderId`，避免直接拿 group order id 去查订单详情。

## 4. 原问题分析

这次真正的问题不是“后端没接口”，而是“前端没有按 CRMEB 实际返回结构消费接口”。

### 4.1 CRMEB 真实返回结构

`createCombined` 最终返回的是 CRMEB `status()` 包装结构，`http.ts` 解包后前端实际拿到的是：

```json
{
  "status": "routine",
  "result": {
    "order_id": 123,
    "config": {
      "timestamp": "1717200000",
      "nonceStr": "xxx",
      "package": "prepay_id=xxx",
      "signType": "MD5",
      "paySign": "xxx"
    }
  }
}
```

这里的关键点：

1. 顶层支付类型字段是 `status`，不是前端原来假定的 `type`。
2. 微信支付参数在 `result.config` 内，不在顶层。
3. CRMEB/overtrue 实际会把支付时间戳字段命名为 `timestamp`，而不是部分示例里常见的 `timeStamp`。
4. `result.order_id` 是 group order id，不一定等于订单详情接口需要的 `store_order_id`。
5. 小程序支付类型是 `routine`，不是前端原来只处理的 `weixin`。

### 4.2 前端原有问题

原结算页存在四个关键问题：

1. 将 `createCombinedOrder()` 直接当成平铺后的支付结果使用。
2. 只识别 `type === 'weixin'`，不识别 CRMEB 小程序支付返回的 `routine`。
3. `buildMiniProgramPaymentOptions()` 严格只读取 `timeStamp`，导致后端返回 `timestamp` 时被误判成“支付参数不完整”。
4. `uni.requestPayment` 使用了 `orderInfo` 形式，这更接近 App 侧，不适合微信小程序 v2/v3 的直接字段模式。
5. 支付成功后直接拿 `order_id` 跳订单详情，存在 group order id / store order id 语义不一致问题。

## 5. 本次前端改动

## 5.1 新增支付归一化 helper

新增文件：

- `src/api/huimaidan.pay.ts`

新增能力：

1. `normalizeHuimaidanOrderPayment(payload)`
   - 将 CRMEB `status/result/config` 结构归一化为前端统一结构。
   - 自动兼容 `timestamp -> timeStamp`、`nonce_str -> nonceStr`、`sign_type -> signType`、`pay_sign -> paySign`。
   - 当后端未包在 `result.config` 中，而是直接平铺在 `result` 或顶层时，也能继续识别。
2. `isWechatMiniProgramPayType(type)`
   - 统一识别 `routine` 和 `weixin`。
3. `buildMiniProgramPaymentOptions(payment)`
   - 构建微信小程序 `uni.requestPayment` 所需参数。
   - 统一从规范化后的字段读取参数，不再因为 `timestamp` 别名问题阻断支付调起。
   - 若缺少 `timeStamp/nonceStr/package/signType/paySign`，直接抛错，不静默降级。

归一化后的前端支付对象格式：

```ts
{
  type: 'routine',
  order_id: 123,
  store_order_id?: 456,
  timeStamp: '1717200000',
  timestamp: '1717200000',
  nonceStr: 'xxx',
  package: 'prepay_id=xxx',
  signType: 'MD5',
  paySign: 'xxx',
}
```

## 12. 本次补充修复：支付成功后订单状态异常

本轮在首版支付接入修复之后，又继续处理了 3 个实际联调问题：

1. 支付成功后出现 3 个订单，且订单状态仍显示“未支付”。
2. 3 个订单编号不同，其中 2 个在商户端订单列表显示“用户已删除”。
3. 平台管理端订单状态仍显示“待付款”。

### 12.1 根因结论

这 3 个问题不是单点故障，而是两条链路叠加：

1. 前端结算页在“创建订单成功但尚未完成支付回调”阶段提前释放了支付锁。
2. 后端惠买单 `pay_result` 只查询本地数据库，不主动向微信支付 v2 查单补偿。

进一步展开：

1. 用户点击“去支付”后，`createCombined` 已经成功建单，但 `checkout.vue` 在 `finally` 中立刻把 `isPaying` 重置为 `false`。
2. 如果用户在支付弹窗拉起、切后台返回、或者页面短暂卡顿时再次点击，就会再次调用 `createCombined`，从而生成额外订单。
3. 真正完成支付的那一笔，如果微信异步通知尚未写回本地库，前端又立刻调用 `pay_result`，就会看到 `paid = 0`。
4. 通用订单列表把 `is_del != 0` 直接渲染成“用户已删除”，这对惠买单重复未支付后被取消的订单是不准确的。
5. 商户端惠买单结算详情页把 `status = 3` 直接解释成“已取消”，但惠买单后端支付成功时本来就会把 `status` 更新为 `3`，因此语义被写反了。

### 12.2 后端真实行为确认

本次已确认惠买单后端单次正常建单只会创建：

1. 1 条 `StoreGroupOrder`
2. 1 条 `StoreOrder`

对应仓储：

- `app/common/repositories/huimaidan/OrderRepository.php`

因此“支付成功后看到 3 个不同订单号”不是后端单请求重复写 3 次，而是前端重复触发建单更符合实际。

修改文件：

- `crmeb/services/MiniProgramService.php`

- `app/common/repositories/huimaidan/OrderRepository.php`

处理方式：

2. 在 `PayStatusService` 中扩展 `routine / weixin / h5 / weixinQr` 查单支持。
3. 在惠买单 `OrderRepository::payResult()` 中增加本地未支付时的主动查单补偿逻辑：
   - 若本地订单已支付，直接返回

1. 不依赖异步通知先到再查结果。
2. 前端在支付成功回跳后立即请求 `pay_result`，也更容易拿到正确状态。
3. 商户端和平台端后续查询到的本地订单状态也会同步变正确。
